# Copy for blogs, articles and documentation

Most page rules ask you to be short. Here the reader came to read, so the job changes: make long text easy to enter, follow and leave.

This file covers the page around the writing, and how to structure it. It does not write the author's article for them. If the user supplies the article, keep their words.

## Blogs and articles

### Who reads it

Someone who searched for a question, or followed a link. They decide within a few lines whether to stay.

Their questions:

1. Is this about what I need?
2. Who wrote it, and when?
3. Can I trust it?
4. Where is the part I want?

### Fact sheet: ask for these

- The article's one point, in a sentence.
- The reader it is written for.
- The author's real name and why they know this.
- Publication and update dates.
- Sources, data, code that is real and working.

### Page parts

| Part | How to write it |
|---|---|
| Title | Says what the reader gets. Specific beats clever: search results and scanners see only this |
| Standfirst | One or two sentences under the title: the point, up front |
| Byline and date | Real author. Show the updated date if it changed |
| Opening | Start with the answer or the situation. Cut the wind-up, which is usually the first paragraph |
| Headings | Each states the point of its section. Reading the headings alone should give the argument |
| Paragraphs | One idea each. Short on a phone |
| Lists and tables | For real lists and comparisons, not for breaking up prose |
| Pull quotes | Only real sentences from the text |
| End | Stop when done. Offer what to read next |

Put the conclusion first (the inverted pyramid). Readers leave at any point, so the most useful thing goes first.

Avoid: "In this article, we will explore…"; a closing "In conclusion" that repeats the piece; invented anecdotes and statistics; a table of contents on a short post.

### Blog index

- Each entry: title, one-line summary, date. The title has to work alone.
- Group by topic only if there are enough posts to fill the groups.
- No empty categories, and no "Latest thoughts on…" filler.

### Tone

The author's own. Most personal voice of any page kind. Keep their opinions, oddities and first person. Do not smooth them.

## Documentation

Good documentation is four different kinds of writing, and mixing them causes most of the trouble. This is the Diátaxis model.

| Kind | Reader | Write it as |
|---|---|---|
| Tutorial | Learning. Does not know what to ask yet | A complete path you lead them down, where every step works |
| How-to guide | Working. Has a specific goal | Steps toward that goal and nothing else. Assume competence |
| Reference | Looking something up | Complete, consistent, dry. Describes and doesn't instruct |
| Explanation | Wants to understand why | Discussion: context, reasons, trade-offs |

Write each page as one kind.

### Writing a how-to page

- Title: exactly what it shows. "How to rotate an API key".
- Open with the goal, in one line.
- Arrange by the reader's task, not by the tool's menus.
- Use conditions: "If you use Docker, run…".
- Leave out teaching and history. Link to them.
- Link to the reference for every option, without listing them all.

### Docs microcopy

- Code samples must work. Copy-paste them and run them.
- Show the expected output.
- Say what version this applies to.
- Warnings go before the step that needs them.
- Headings are nouns or tasks a reader would search for.

### Tone

Direct, second person, present tense. "Run the command", and not "You will want to run the command". No marketing. No "simply" or "just": if it were simple they would not be reading.

## Checklist

- [ ] The title says what the reader gets.
- [ ] The first paragraph delivers something.
- [ ] Reading the headings alone gives the argument.
- [ ] Author, date and sources are real.
- [ ] Docs: each page is one of the four kinds.
- [ ] Docs: every code sample was run.
